# Decisions

1. **One Worker, one D1 database, no framework** (2026-10-23, Avi). Serves the pages, the API and the Access check. A couple of weeks of life does not justify more.
2. **No backups; D1 Time Travel only** (Avi). 30 days of point-in-time restore covers the lifetime of the app.
3. **Access for sign-in, with one-time PIN for volunteers without Gmail** (Avi). Emails go in the Access policy. Admins are the `ADMIN_EMAILS` Worker secret (it began as a variable in `wrangler.jsonc`; Avi moved it to a secret so the emails are not in git and changing them needs no deploy), because the Cloudflare team can add volunteers and no app-side user table is needed. About 20 volunteers fits Access's free tier.
4. **Everyone sees everything** (Avi). The current sheet works that way; the app adds who may change what, not who may see what.
5. **People are keyed by normalized first name, last name and address** (Avi). The state's sheets do not reliably carry a voter id. Near-misses are reported on upload, never merged.
6. **Only an upload cures** (Avi). A volunteer's "Contacted" is a claim; the state's data is the verification. A contacted person still on a later sheet is flagged for the admin and returns to needs-contact with the same volunteer.
7. **Claims do not expire and are not capped** (Avi). Volunteers and admins can release them.
8. **No distance sorting** (Avi). Addresses only, no geocoding. Sort by days uncured, city, precinct, party or name. *Reversed by 21.*
9. **JavaScript is allowed** (Avi). The design system's no-JS rule is for the public site; this is an internal tool. The CSP stays `'self'`.
10. **CSV upload, not xlsx** (Avi). The admin exports the LD8 tab; parsing xlsx without dependencies is fragile.
11. **One Chromium browser in CI** (this repo). It is an internal tool for staff and volunteers; WebKit and Firefox smoke runs are `SMOKE_BROWSER=webkit|firefox` away if needed.
12. **Admins set a grace period for contacted ballots** (Avi, 2026-10-23). The state's sheet is uploaded daily and runs behind the calls, so how long a ballot a volunteer marked contacted may stay on the list is counted in uploads (`graceCycles`, 0 to 30, default 1; one row in `settings`, `grace_cycles`). Past it the ballot is an unsuccessful cure: flagged `still_uncured`, back to needs contact, same volunteer. It replaces the earlier rule that compared the contact time with the previous upload's. Only people marked contacted count; nobody is ever closed out by time on the list.
13. **Every pull request runs Chromium, Firefox and WebKit; merging to `main` deploys** (Avi, 2026-10-23). The repository is public, so standard GitHub-hosted runners are free and there is no reason to save minutes: every job is on `ubuntu-latest`, and the three browsers run as parallel jobs on each pull request (`ci-proposed/ci.yml`). `ci-proposed/deploy.yml` deploys on a push to `main`, from the `production` environment, and by hand for a redeploy. It does not run migrations. This replaces an earlier plan (avi.me's) that ran the extra browsers only on a release tag, to save billed minutes. Firefox and WebKit cannot run on the agent VM, so their first run is the first pull request that carries the workflow. That run showed one Playwright-WebKit quirk, a CSP "refused to apply a stylesheet" console line on pages with a `<select>` (avi.me hits the same one and bisected it to the `<select>`); `tools/lib/webkit-quirks.ts` lists it, the smoke test counts and prints what it ignored, and anything else still fails.
14. **LD8 design doc first, Frostline for what it lacks; Frostline's spacing rules** (Avi, 2026-10-23). Both systems are used: the LD8 tokens, type, logo, header and call-to-action button, and Frostline's components for everything else (cards, badges, banners, fields, tables, tiles, toasts, segmented control, disclosure, confirm). Frostline is vendored verbatim (`vendor/frostline/`, 1.11) and its token names are mapped onto LD8 values in `public/tokens.css`, so none of its palette or fonts ships. Spacing is Frostline's: gap on containers, never margins on children, each step for its role, nothing in between. Details and the token table are in `docs/design.md`.
15. **Admins can delete every voter while the app holds test data, and a setting turns it off** (Avi, 2026-10-23). **Start over** deletes voters, notes and upload history and keeps volunteers, settings and the audit log (which records it). It is behind a dialog, needs `confirm: "delete all voters"` in the request, and exists only while `ALLOW_RESET` is `"true"` in `wrangler.jsonc`: set it to `"false"` and deploy before real data goes in. D1 Time Travel can undo a reset for 30 days either way.
16. **Dependabot runs weekly, one pull request per bump; mapping libraries ship as npm dev dependencies** (Avi, 2026-10-25). `.github/dependabot.yml` watches npm and the SHA-pinned GitHub Actions, with a one-week cooldown after a release. Frostline is vendored by hand, so Dependabot cannot see it. The mapping libraries for the planned map (`maplibre-gl`, `pmtiles`) are on npm, so they are pinned dev dependencies and `tools/build.sh` copies their built files into `public/`, which lets Dependabot track them; the CSP stays `'self'` only apart from what MapLibre needs. What no manifest covers (the basemap glyph and sprite files, the `.pmtiles` extract) is recorded in `vendor/README.md` and updated by hand.
17. **Built for the free Workers and D1 plans: count rows read and written** (2026-10-25). Free D1 allows 5 million rows read and 100,000 rows written a day, and counts every index entry as a row written. So: Find people never counts (it asks for one person more than it shows), its filter values are stored by the upload (`settings.facets`), and its city, precinct and sort orders have partial indexes on the open pool (migrations 0002 and 0003); an upload rewrites only the people whose details or status changed. Each index costs a row written per person per insert, so add one only for a query the pages run. Free Workers also allow about 10 ms of CPU a request, which a large CSV parse exceeds (about 90 ms for 10,000 rows, measured in Node); the Workers Paid plan or an upload split into many requests is the way past that.
18. **A sheet is read in the admin's browser and applied in SQL** (Avi, 2026-10-25). On the free Workers plan a request gets about 10 ms of CPU, and parsing a 10,000-row CSV takes about 90 ms. So the browser reads the file (`src/sheet.ts`), sends the people about a hundred at a time into a staging table (`upload_rows`, migration 0004), and the Worker compares and applies them as set operations inside D1 (`worker/uploads.ts`), where the time is not Worker CPU. The apply is still one atomic batch, and it refuses unless exactly the announced number of people arrived. The plain-function version of the rules (`tools/lib/plan.ts`) stays as the reference, and `tools/test-upload-sql.ts` requires the SQL to match it on random states. Measured: about 0.2 ms of JavaScript for a 100-person request (Node, database stubbed). The old routes that took the CSV in a request body are gone.
19. **An admin can mark a possible match as the same person; the upload then updates the old record** (Avi, 2026-10-25). The state corrects names and addresses between dumps, and a corrected record is a different key: the old person was cured and a stranger added, losing the notes and the volunteer. A pair marked as the same person (`upload_merges`, migration 0005, kept with the staged sheet) makes the upload re-key the old record and update it. Only pairs the list offers can be marked, one pair per person. A third rule (same first name and address, another last name) joins the other two. Matching stays exact on the normalized key; there is no similarity scoring and no address service.
20. **Keys are normalized locally; the Census geocoder is not part of the key** (Avi, 2026-10-25). Names keep only letters and digits; addresses are cut to the street line and put in USPS Publication 28's standard words, with the word before a unit number dropped and the number kept. Existing data was throwaway, so there is no migration: the keys are versioned (`KEY_VERSION`, `settings.key_version`) and the upload page warns, before anything is applied, when the people already here were keyed the old way. The Census geocoder is for coordinates, stored beside the address; it is not used for the key because a key must come out the same for the same sheet every time, in the browser, with no network call, and a geocoder's answer depends on its match score and on when its data was last updated, so keys would drift between dumps, which is the problem this solves.

21. **Addresses are geocoded by an admin, from the Worker, with the US Census batch geocoder** (Avi, 2026-10-25; reverses 8, "No distance sorting"). It is admin-triggered, not part of an upload, so an upload stays fast and a Census outage cannot stop one. The Worker, not the browser, makes the call, so the CSP stays `'self'` only and there is one place that sends addresses. Only an id and a street address go; the page shows the first lines of the next request, and every request has an audit row. A couple of hundred people a request keeps the Worker's own CPU under the free plan's limit (the wait for the Census does not count). The coordinates are stored beside the address and are never part of a person's key, which must come out the same for the same sheet every time. Before the first run on real voters, Avi reads the Census geocoder's terms of use: voter addresses leave the app.
22. **Unplaced addresses are listed, can be tried again, and get the middle of their ZIP, marked approximate** (Avi, 2026-10-25). A typical geocoder miss is a PO box, a rural route, a new street or a typo, and without a place a person would never turn up in a distance search or on the map, exactly when their address is awkward. So each one gets the average place of the people the geocoder did place in their ZIP (needing at least five, so a middle is never one person's house) and `approximate = 1`, and the admin can see them, copy their addresses, download the list and ask the geocoder again. The map must draw approximate places in a different color from exact ones, with a legend. Approximate places are never used to work out a ZIP's middle, and are cleared when an upload changes the address.
23. **Volunteers can save where they are for "near me"; it stays rounded and private** (Avi, 2026-10-25). Saving it is optional, from the device or as the middle of a ZIP, rounded to 0.01 degrees before it is stored, visible only to that volunteer (admins do not see it either), absent from the audit log, and clearable. The Permissions-Policy allows geolocation for our own pages only (`geolocation=(self)`), and the browser still asks each volunteer. A distance sort needs a radius, so a request reads a band of the map from `people_pool_place` (migration 0008) instead of the whole pool: on the free plan a sort over 10,000 people would use the day's reads in a few hundred requests. Distance is worked out in SQL on a flat map with only + - * (a degree of latitude in miles, a degree of longitude scaled by the cosine of the saved place's latitude): D1 refuses SQLite's math functions ("not authorized to use function: power"), which broke every search by distance, the map's radius and the town name in production until 2026-10-27, and which SQLite on a laptop allows, so the test database now refuses them too (`tools/lib/sqlite-d1.ts`). Over the 100 miles the largest search allows the flat map is within a hundredth of a percent of the great-circle distance. The index reads the smallest latitude and longitude box that holds the circle, and the circle itself is checked after it. The tests compare who is in or out, and every distance shown, with the spherical law of cosines.
24. **The geocoder gets the street without its unit, a second try with the street alone, and non-exact matches are guesses** (Avi, 2026-10-25). Tested against the real Census geocoder with three real addresses from the unplaced list: a bare unit number after the street type made one miss (fixed by dropping the unit); another missed only because the sheet's city and ZIP (Mesa 85201) disagree with the Census's (Tempe 85281) and matched exactly with neither (so a retry also sends the street alone, believed only within 15 miles of the middle of the person's ZIP); a third matched under no variant. A match the Census calls non-exact can land on the wrong side of a street (a `W` came back as `E`), so it is stored as approximate.
25. **An admin can place an unplaced person by hand** (Avi, 2026-10-25). The Census will not find every address (one of three real ones from the list matched under no variant), and a ZIP's middle is a guess. So the list takes coordinates, written as a map shows them. The place is stored with who gave it (`placed_by`, migration 0009) and counts as exact; the geocoder's own verdict is left as it was, so the person stays in the list and a later lookup can still replace the hand-set place with an answer from the Census, but a miss cannot take it away. It is never part of anyone's key, and is cleared with the rest when an upload changes the address.
26. **The map: MapLibre and PMTiles from our own origin, the tiles in R2, the pins in one request** (Avi, 2026-10-26). A Protomaps basemap cut to a box around Arizona State Senate District 8 (the Census's 2026 boundary, `-112.0129,33.3765,-111.6399,33.5816`, plus about two miles) is one `.pmtiles` file. Workers static assets cap a file at 25 MiB and a gitignored file would not be in CI's deploy, so it lives in an R2 bucket (`cure-tracker-tiles`, bound as `TILES`), uploaded once by hand and served by the Worker with byte ranges behind Access. Tiles never leave our origin, so no outside service learns where volunteers look, and the CSP stays `'self'` (MapLibre 6 loads its worker from a file beside itself, so `worker-src 'self'` is enough, no `blob:`). `maplibre-gl`, `pmtiles` and `@protomaps/basemaps` are dev dependencies (the last is added to CLAUDE.md's list), copied or compiled into `public/lib/` by `tools/build.sh`; Dependabot tracks them. Street names need glyph files, which are not on npm: three Noto Sans faces, three Unicode ranges each, from Protomaps' `basemaps-assets`, are vendored (`vendor/map-fonts/`, `vendor/README.md`); layers that draw an icon are left out, so there is no sprite. Pins come from `GET /api/map` as `[id, lat, lon, guess]`, once for the whole district, because every ask reads the pool's places from `people_pool_place` (about 10,000 rows for a pool of 10,000, of the free plan's 5 million a day). Exact places are a solid dot, guesses a ring in another color, with a legend (decision 22).
27. **Precinct organizers: volunteers who can move people in some precincts, granted in the app** (Avi, 2026-10-26). Site admins stay the `ADMIN_EMAILS` secret and keep the uploads, geocoder, settings, audit log, reset and the grants. Organizers are a table (`organizers`, migration 0010) that site admins edit on the admin page: a row per precinct, or `*` for all, so a grant changes without a deploy. An organizer's reach is the voter's precinct, checked on every move, flag dismissal and bulk move; a voter with a blank precinct can be moved by any organizer. Everyone still sees every voter (the pool is how people claim), so the extra power is only to move and clear flags. Grants are limited to the district's list of precincts (56, with their cities, given by Avi on 2026-10-26 and kept in `src/precincts.ts`), matched ignoring case; an upload warns about sheet precincts that are not on it, so a misspelling shows up when it arrives. The list is a list of names, not voters.
28. **The map shows claimed people, and who has them; "Contacted" is a promise, not a cure** (Avi, 2026-10-26, from an organizer's feedback). Claimed people who are not cured are pins (yellow, red when a claim has had no claim, move, status change or note for 3 days), and pressing one shows the volunteer's name and email and their last activity to every signed-in volunteer, so volunteers working a block or an apartment complex can help each other and an organizer can see claims that sit. They already see every volunteer's list, so nothing new is exposed beyond the pin's place. A partial index (migration 0011) keeps the claimed read cheap. Cured stays upload-only and no "promised" status was added: the Contacted help text now says a relative's promise is not a cure.
29. **Organizers assign from Find people and the Map, and an admin emails the volunteer by hand, once for a batch** (Avi, 2026-10-28). The assign route already existed for the admin page; Find people and the Map now offer it to organizers for the people in their precincts. The email comes from `admin@azld8cures.com` through the Worker's `send_email` binding (`EMAIL`), says who assigned a voter and links to the site, and carries no voter data, so a forwarded or leaked email exposes nothing. "Verified" needs no extra step: a volunteer row is created only from a signed-in Access identity, and Access has proved the address by a one-time PIN or Google. Assigning sends nothing (Avi, the same day: an automatic email after the first of ten assignments would have told the volunteer about one): the assignment marks the person (migration 0015) and the admin page has a button that emails each volunteer once about everyone marked. Without the binding, or when sending fails, nothing is emailed, the marks stay, and assigning still works.
30. **Admins invite people by email; Access stays the only gate, and the policy is edited by hand** (Avi, 2026-10-28). The adoption problem is that many volunteers are older and do not know how to sign in, so an admin pastes addresses and each gets an email with numbered steps (migration 0014 keeps the list, so the admin page shows who has signed in). Three ways to let invitees through Access were weighed: an invite list checked by the Worker (changes the security model of decision 3), the Worker editing the Access policy through the Cloudflare API (needs a token that can grant anyone access to voter data, stored as a Worker secret), and sending the email only while an admin adds the addresses to the policy by hand. Avi chose the last: nothing in the app can widen who sees voter data. The cost is one manual step, which the page eases with a copy button. Sending to people who are not in the account needs the Workers Paid plan (Email Sending, $5 a month, 3,000 emails included); sending only to verified destinations is free.
